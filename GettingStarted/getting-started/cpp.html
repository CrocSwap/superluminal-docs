    Getting Started with the C++ Client¶

    The reference api_client is a C++20 terminal application for connecting to Superluminal, viewing native maker and taker books, monitoring a trading account, and submitting, modifying, and cancelling signed orders.

    It is a reference application rather than a complete binding for every public API command. See the public API reference when building a custom integration.

    Requirements¶

    You need:

    • the supplied C++ client source bundle;
    • a C++20 compiler;
    • Meson and Ninja;
    • pkg-config, OpenSSL, and libsodium; and
    • a Solana-format Ed25519 keypair JSON file for your Fogo wallet.

    On Ubuntu or Debian:

    sudo apt-get update
sudo apt-get install -y \
  build-essential \
  libssl-dev \
  libsodium-dev \
  meson \
  ninja-build \
  pkg-config

    The source bundle vendors FTXUI, IXWebSocket, and simdjson.

    Build the client¶

    From the root of the standalone C++ source bundle:

    meson setup build
meson compile -C build

    The executable is written to:

    build/api_client/api_client

    Confirm the binary before connecting:

    ./build/api_client/api_client --version

    Fund the wallet¶

    The bundle includes the source funding utility. Fund subaccount 0 before starting the client:

    cd funding-tools
bun install --production --frozen-lockfile
bun run fund:testnet --keypair /path/to/wallet.json
cd ..

    Wait for Funding complete.. The funding utility opens an authenticated session, and the public gateway permits one authenticated session per wallet, so running it while the client is connected will preempt the client.

    See Funding accounts for keypair requirements, deposit-address derivation, faucet limits, and manual deposits.

    Start the client¶

    ./build/api_client/api_client \
  --ws wss://testnet.slx.fi/ws \
  --keypair ./wallet.json \
  --subaccount_id 0 \
  --partition_id 0x01

    Arguments:

    • --ws: WebSocket endpoint; both ws:// and wss:// are supported.
    • --keypair: Fogo wallet keypair JSON file.
    • --subaccount_id: trading subaccount displayed by the application.
    • --partition_id: signed-message partition; public testnet uses 0x01.
    • --feed_ids: optional comma-separated market IDs. When omitted, the client subscribes to every active market returned by /v1/symbology.

    The client fetches symbology from the HTTP origin corresponding to --ws, then authenticates the wallet and starts the account and market subscriptions.

    Connection flow¶

    The client performs these steps automatically:

    1. Fetch GET /v1/symbology.
    2. Send auth_wallet with the wallet public key.
    3. Sign the returned auth_challenge locally.
    4. Send auth_response and wait for ack accepted.
    5. Send subscribe_account.
    6. Request the newest account order-history page.
    7. Subscribe to the selected active markets.

    The first private account message is normally AccountSnapshot. Later account messages report accepted orders, rejects, fills, settlements, collateral, funding, modifications, and cancellations.

    Market data¶

    Native subscribe_market streams contain two book views:

    • bookType: "maker"
    • bookType: "taker"

    The client synchronizes them independently and combines them in its ladder. It also consumes Trade events. If it receives stream_reset, it discards the affected local book and resubscribes.

    Market IDs and integer scaling are deployment data. Fetch them rather than hardcoding them:

    curl --fail https://testnet.slx.fi/v1/symbology

    Use px_exponent, tick_size, and size_decimals when converting human prices and quantities to raw wire integers.

    Submit an order¶

    The order ticket creates and signs a signed_order proof locally. Choose:

    • market;
    • buy or sell;
    • quantity;
    • limit, mark-to-mid, or market order;
    • GTC or IOC where applicable; and
    • explicit MAKER or TAKER role.

    Role is not inferred. Market orders require TAKER. For a protected market order, provide a reference price and slippage from 1 to 1,000,000 ppm. Leave both fields empty for an unrestricted market order.

    Sending the command successfully is not the final order result. Observe the private account stream:

    • ack rejected or ack busy reports a local command failure;
    • OrderAccepted confirms admission to the account stream;
    • OrderReject reports an asynchronous rejection; and
    • Fill, FillSettled, and FillBusted report execution and settlement.

    Modify or cancel an order¶

    Select a working order in the TUI to modify or cancel it. The client signs the corresponding command and waits for ModifyAck, ModifyReject, CancelAck, or CancelReject on the account stream.

    First-run checklist¶

    1. Check https://testnet.slx.fi/healthz returns ok.
    2. Fetch /v1/symbology and confirm at least one active market.
    3. Fund the wallet and wait for Funding complete..
    4. Start api_client with the same keypair and subaccount 0.
    5. Confirm AccountSnapshot and market data appear.
    6. Submit a small order and observe its private lifecycle events.
    7. Cancel it if it remains working.

    Common problems¶

    • Session preempted: another connection authenticated the same wallet.
    • Invalid symbol: refresh /v1/symbology and use an active market ID.
    • Invalid price grid: encode the price using current px_exponent and tick_size.
    • Missing balance: complete funding and wait for UserCollateralUpdate before starting the client.
    • Book reset: discard the affected book and resubscribe; the reference client does this automatically.

    For complete message schemas and rejection reasons, use the public API reference.
