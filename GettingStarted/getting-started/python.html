    Getting Started with the Python Client¶

    The standalone Python SDK includes a Textual terminal application for viewing native maker and taker books, monitoring a trading account, and submitting, modifying, and cancelling signed orders.

    It is a reference client rather than a complete binding for every public API command. See the public API reference when building a custom integration.

    Requirements¶

    You need:

    • the supplied python_gateway_client directory;
    • Python 3.12 or newer;
    • internet access to install pinned dependencies from PyPI; and
    • a Solana-format Ed25519 keypair JSON file for your Fogo wallet.

    The SDK is self-contained and installs into its own virtual environment.

    Install the SDK¶

    From python_gateway_client:

    ./scripts/bootstrap_venv.sh

    This creates .venv locally and installs the pinned runtime dependencies. It does not modify the system Python installation.

    Fund the wallet¶

    The bundle includes the source funding utility. From python_gateway_client, fund subaccount 0 before starting the Python client:

    cd funding-tools
bun install --production --frozen-lockfile
bun run fund:testnet --keypair /path/to/wallet.json
cd ..

    Wait for Funding complete.. Do not run the funding utility while the Python client is connected: the public gateway permits one authenticated session per wallet, so the newer session would preempt the older one.

    See Funding accounts for keypair requirements, deposit-address derivation, faucet limits, and manual deposits.

    Find active markets¶

    Fetch symbology before choosing --feed-id values:

    curl --fail https://testnet.slx.fi/v1/symbology

    At the time of writing, public testnet exposes BTC (1), ETH (2), and SOL (6). Treat the response as authoritative because markets and IDs may change.

    Use px_exponent, tick_size, and size_decimals when converting human prices and quantities to raw wire integers.

    Start the TUI¶

    From python_gateway_client:

    ./.venv/bin/sl-tui \
  --ws wss://testnet.slx.fi/ws \
  --keypair ./wallet.json \
  --subaccount 0 \
  --feed-id 1 \
  --feed-id 2 \
  --feed-id 6 \
  --partition-id 0x01

    Arguments:

    • --ws: WebSocket endpoint. The default is local development, so always pass the public wss:// endpoint for testnet.
    • --keypair: Fogo wallet keypair JSON file.
    • --subaccount: trading subaccount displayed by the application.
    • --feed-id: market ID to subscribe to; repeat it for each market.
    • --partition-id: signed-message partition; public testnet uses 0x01.
    • --auth-expiry-seconds: optional nonzero authentication lifetime.

    Connection flow¶

    The client performs these steps automatically:

    1. Fetch GET /v1/symbology.
    2. Send auth_wallet with the wallet public key.
    3. Sign the returned auth_challenge locally.
    4. Send auth_response and wait for ack accepted.
    5. Send subscribe_account.
    6. Subscribe to every configured market.

    The first private account message is normally AccountSnapshot. Later account messages report accepted orders, rejects, fills, settlements, collateral, funding, modifications, and cancellations.

    Market data¶

    Native subscribe_market streams contain two book views:

    • bookType: "maker"
    • bookType: "taker"

    The Python client synchronizes the views independently and combines them in the ladder. It also consumes Trade events. If it receives stream_reset, it discards the affected local book and resubscribes.

    Submit an order¶

    The order ticket creates and signs a signed_order proof locally. Choose:

    • market;
    • buy or sell;
    • quantity;
    • limit, mark-to-mid, or market order;
    • GTC or IOC where applicable; and
    • explicit MAKER or TAKER role.

    Role is not inferred. Market orders require TAKER. For a protected market order, provide a reference price and slippage from 1 to 1,000,000 ppm. Leave both fields empty for an unrestricted market order.

    Sending the command successfully is not the final order result. Observe the private account stream:

    • ack rejected or ack busy reports a local command failure;
    • OrderAccepted confirms admission to the account stream;
    • OrderReject reports an asynchronous rejection; and
    • Fill, FillSettled, and FillBusted report execution and settlement.

    Modify or cancel an order¶

    Select a working order in the TUI to modify or cancel it. The client signs the corresponding command and waits for ModifyAck, ModifyReject, CancelAck, or CancelReject on the account stream.

    Use the SDK from Python¶

    The reusable pieces live under dfba_client:

    • GatewayClient handles authentication, subscriptions, orders, modifies, cancels, and subaccount transfers.
    • WebSocketTransport owns the reconnecting WebSocket loop.
    • commands contains JSON request encoders.
    • codec validates and decodes gateway messages.
    • signer loads keypairs and creates signed command proofs.

    The TUI is an example consumer of these modules. Applications can construct a ClientConfig, initialize GatewayClient, and run WebSocketTransport without using Textual.

    First-run checklist¶

    1. Check https://testnet.slx.fi/healthz returns ok.
    2. Fetch /v1/symbology and select active market IDs.
    3. Install the SDK with ./scripts/bootstrap_venv.sh.
    4. Fund the wallet and wait for Funding complete..
    5. Start sl-tui with the same keypair and subaccount 0.
    6. Confirm AccountSnapshot and market data appear.
    7. Submit a small order and observe its private lifecycle events.
    8. Cancel it if it remains working.

    Common problems¶

    • Session preempted: another connection authenticated the same wallet.
    • Configured feed missing: refresh /v1/symbology and use active IDs.
    • Invalid price grid: encode the price using current px_exponent and tick_size.
    • Missing balance: complete funding and wait for UserCollateralUpdate before starting the client.
    • Book reset: discard the affected book and resubscribe; the reference client does this automatically.

    For complete message schemas and rejection reasons, use the public API reference.
