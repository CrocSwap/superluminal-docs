    Superluminal Public API¶

    This reference defines the public Superluminal HTTP and WebSocket API. For a guided setup, start with the C++ client, Python client, or funding guide.

    Public Testnet¶

    • HTTP base: https://testnet.slx.fi
    • WebSocket: wss://testnet.slx.fi/ws
    • EVM chain: Arbitrum Sepolia (421614)
    • EVM RPC: https://sepolia-rollup.arbitrum.io/rpc

    Fetch GET /v1/evm/addresses from the gateway instead of hardcoding EVM contract addresses.

    Transport and Limits¶

    WebSocket¶

    • Max inbound frame size: 256 KiB
    • Max inbound text command size: 64 KiB
    • Max signed proof payload size: 512 bytes
    • Per-connection inbound WebSocket message rate limit, including data frames and ping/pong control frames:
    • default rate of 3000 messages/minute
    • default burst capacity of 150 messages
    • deployment and wallet-specific limits may differ
    • exceeded connections are closed with msg_rate_limit_exceeded
    • order-like commands are counted by this same limiter:
      • signed_order
      • signed_cancel
      • signed_modify
      • signed_conditional_group
      • signed_conditional_parent
      • signed_conditional_cancel
    • deposit/withdraw commands are also counted by this same limiter.
    • application-level ping messages and WebSocket ping/pong control frames are counted by this same limiter.
    • invalid or unauthenticated messages are counted before command validation so malformed-message floods cannot bypass the limit.
    • The burst capacity allows brief traffic above the per-minute refill rate; clients must then wait for capacity to refill.
    • Ping/pong:
    • Server sends ping every 20s.
    • Read deadline is 120s and extended on pong.

    Origin policy¶

    • Browser connections are checked against the deployment's origin allowlist at WebSocket upgrade.
    • Non-browser API clients may omit the Origin header.

    Integer encoding¶

    Order identifier response encodings are chosen by field, not by the size of each value. JavaScript and TypeScript Number cannot represent every integer above 2^53 - 1; decimal strings preserve 64-bit IDs and can be converted directly to bigint.

    The response encodings are:

    • client_instruction_id and original_client_instruction_id are always quoted, unsigned decimal strings, including in TP/SL account snapshots. Clients must reject JSON numbers for these fields and decode them losslessly.
    • external_order_id is always a JSON integer number. Gateway-issued values do not exceed JavaScript's maximum safe integer, 9007199254740991. Clients must reject decimal strings for this field.

    The signed binary envelopes still encode these identifiers as little-endian uint64 values before base64 encoding; the rule above applies to JSON fields.

    Separately, last_seq on /v1/user-volume and /v1/open-interest, and subaccount_id on /v1/user-volume subaccount records, may be emitted as JSON numbers through 9007199254740991 and decimal strings above that limit. JavaScript and TypeScript clients must preserve those dual-form values as bigint or lossless decimal strings, never Number.

    Public request_id64 values reserve bit 63 and therefore cannot exceed 9223372036854775807.

    Ordinary order and collateral submission commands restrict subaccount IDs to 0..31, although the signed wire field is uint64. This also applies to user_deposit_address and both subaccounts in a transfer.

    Numeric units¶

    Price, base quantity, monetary amounts, and rates use different scales:

    Value Conversion to human units
    Market price (price, mark_price, perp_price, TP/SL trigger prices) raw * 10^px_exponent, in quote currency per base unit
    Base quantity (qty, remaining_qty, filled_qty, settled_qty, reduced_qty, net_qty) raw * 10^(-size_decimals), in base units
    Collateral, fees, cost basis, PnL, funding amounts raw / 1000000, in USD accounting units
    Funding rates/indices (premium_e8, max_funding_rate_e8, cum_funding_index_e8, prev_funding_index_e8, last_funding_index_e8) raw / 100000000, a dimensionless rate/index
    Fee rates and price offsets in *_ppm raw / 1000000, a dimensionless fraction
    Margin and other rates in *_bps raw / 10000, a dimensionless fraction

    The six-decimal monetary scale is fixed across markets. It does not come from px_exponent or size_decimals, and quote: "USDC" does not change it. For example, collateral_balance: 10000000000 means 10000 USD, fee: -1000 means a 0.001 USD rebate, and funding_delta: -25000 means a 0.025 USD funding debit. A funding index of 25000 instead means 0.00025; it is not a USD balance.

    The monetary rule applies to:

    • collateral_balance, collateral_delta, collateral_amount, and owe_to_insurance;
    • fee, applied_fee, accrued_fee, pending_fees, and fees_accrued_after;
    • cost_basis, remaining_cost_basis, realized_pnl, and monetary PnL fields;
    • funding_delta, funding_accrued, accrued_funding, and net_funding_after;
    • deposit, withdrawal, and collateral-transfer amounts, including actual_deposit, total_deposit, requested_withdraw_amount, and actual_withdraw_amount.

    Signed balances, deltas, fees, position cost basis, PnL, and funding amounts are signed integers; deposit/withdraw request amounts are unsigned. Positive fees are charges and negative fees are rebates. Positive funding amounts are credits and negative funding amounts are debits. net_qty and position cost_basis are signed; an order or fill qty is an unsigned magnitude whose direction comes from side.

    AccountSnapshot.subaccounts[].collateral_balance already includes accrued fees and funding. Do not subtract accrued_fee or add accrued_funding again when displaying that balance.

    Configuration fields explicitly suffixed _usd, such as min_deposit_amount_usd in /v1/config, are human USD amounts, not raw six-decimal integers. Token amounts in EVM transactions use the collateral token's decimals; do not infer arbitrary token precision from market symbology. Vault shares are share counts, not collateral amounts.

    JSON integer encoding and numeric scaling are separate rules. Private account monetary fields and most sequence/timestamp fields are JSON numbers; implementations must parse large integers losslessly rather than round them through a JavaScript Number. The string-only instruction-ID rule above still applies.

    HTTP API¶

    GET /healthz¶

    Returns:

    ok

    Status: 200.

    GET /v1/config¶

    Returns the public exchange configuration.

    Sample response:

    {
  "taker_fee_ppm": 100,
  "maker_fee_ppm": -10,
  "environment": "testnet",
  "min_deposit_amount_usd": 5,
  "deposit_withdraw_fee_usd": 1,

  "vault_creation_fee_usd": 100,
  "leader_share_bps": 500,
  "leader_fee_bps": 1000
}

    Market identifiers and scaling metadata are delivered as the initial SymbologySnapshot on every WebSocket connection. They are not exposed over HTTP.

    GET /v1/evm/addresses¶

    Returns public EVM deployment metadata needed by clients to compute user deposit addresses and submit EVM token transfers.

    Sample response:

    {
  "version": 1,
  "collateral": "0x1111111111111111111111111111111111111111",
  "gateway": "0x2222222222222222222222222222222222222222",
  "fee_recipient": "0x3333333333333333333333333333333333333333",
  "user_deposit_init_code_hash": "0x4444444444444444444444444444444444444444444444444444444444444444"
}

    Fields:

    • version: response schema version.
    • collateral: ERC20 collateral token address on the EVM chain.
    • gateway: deployed EVMVault address on the EVM chain.
    • fee_recipient: EVM fee recipient address.
    • user_deposit_init_code_hash: CREATE2 init code hash for UserDeposit.

    Status:

    • 200: EVM address metadata is configured.
    • 503: gateway has no EVM address metadata configured.

    GET /v1/user-volume¶

    Returns the 100 wallets with the largest aggregate traded volume across all subaccounts. volume is the exact raw sum of fill_price * fill_qty and is a decimal string. last_seq is the account-persistor checkpoint at query time.

    {
  "last_seq": 12345,
  "users": [
    {
      "wallet_pubkey": "<base58 wallet>",
      "volume": "1234567890",
      "subaccounts": [
        {
          "subaccount_id": 0,
          "volume": "1234567890"
        }
      ],
      "last_updated": "2026-08-18T12:00:00Z",
      "last_seq": 12340
    }
  ]
}

    Status:

    • 200: leaderboard returned.
    • 503: notifier leaderboard source is unavailable.

    GET /v1/open-interest¶

    Returns the 100 wallets with the largest aggregate open interest. Values are raw collateral units encoded as decimal strings. last_seq is the account-persistor checkpoint at query time.

    {
  "last_seq": 12345,
  "users": [
    {
      "wallet_pubkey": "<base58 wallet>",
      "open_interest": "1234567890"
    }
  ]
}

    Status:

    • 200: leaderboard returned.
    • 405: method is not GET.
    • 503: notifier leaderboard source is unavailable.

    POST /info¶

    Accepts a Hyperliquid-style info request body.

    Supported request:

    { "type": "meta" }

    Returns active symbology as a minimal Hyperliquid-compatible metadata response:

    {
  "universe": [
    {
      "name": "BTC",
      "szDecimals": 5
    }
  ]
}

    Notes:

    • Method must be POST.
    • Only {"type":"meta"} is supported.
    • Non-empty dex is rejected.

    Hyperliquid Compatibility¶

    The gateway exposes a small, public market-data surface intended to be Hyperliquid-compatible.

    For lowest latency, clients should prefer the native subscribe_market market-data API over the Hyperliquid compatibility layer. The native stream forwards raw gateway market data without the extra channel wrapping, filtering, and format conversion used by the HL-compatible channels.

    Maker/taker behavior:

    • Native subscribe_market exposes raw public book events for both maker and taker books.
    • Raw BookSnapshot, BookDelta, and stream_reset book events are tagged with bookType.
    • Hyperliquid-compatible derived book channels are maker-only:
    • l2Book is built from the maker book only.
    • bbo is built from the maker book only.
    • allMids is computed from maker-book BBOs only.
    • If a client needs taker-book data, it must use the native raw subscribe_market stream and filter by bookType: "taker".

    Supported HL-compatible endpoints:

    • POST /info with {"type":"meta"}
    • WebSocket subscribe / unsubscribe for:
    • l2Book
    • bbo
    • trades
    • allMids

    This compatibility surface is market-data only. Authentication, private account streaming, and signed order entry use the native Superluminal API.

    HL WebSocket subscription ack shape¶

    Successful HL-style subscribe commands return:

    {
  "channel": "subscriptionResponse",
  "data": {
    "method": "subscribe",
    "subscription": {
      "type": "trades",
      "coin": "BTC"
    }
  }
}

    Notes:

    • The response uses a nested data.subscription object.
    • The subscription object reflects the normalized subscription accepted by the gateway.
    • HL-style unsubscribe does not emit an ack; the gateway just stops delivering that channel.

    Auth and Session Rules¶

    Auth gating¶

    • Public commands require no authentication: subscribe_market, unsubscribe_market, native candle commands, Hyperliquid-style l2Book / bbo / trades / allMids subscribe/unsubscribe, and ping.
    • Private/account actions and signed submit require authentication.

    Auth mode¶

    Each WS connection authenticates with wallet challenge mode: auth_wallet -> auth_response.

    Exactly 1 active authenticated WS per wallet¶

    This gateway enforces one active authenticated WS per bound wallet.

    What this means:

    • If a new connection authenticates/binds the same wallet, the previous connection is preempted.
    • The old connection receives:
    {
  "type": "session_preempted",
  "reason": "new_session_authenticated"
}
    • Then old connection auth state is cleared and socket is disconnected.

    Concrete examples:

    • API bot has wallet W authenticated/bound on WS-1. The same wallet authenticates on WS-2: WS-1 gets session_preempted and disconnects.

    Command Reference (with examples)¶

    Symbology bootstrap and updates¶

    Every public WebSocket connection receives one full snapshot when it connects:

    {
  "type": "SymbologySnapshot",
  "version": 123,
  "markets": [
    {
      "id": 7,
      "symbol": "BTC",
      "quote": "USDC",
      "pyth_feed_id": 1,
      "max_funding_rate_e8": 10000,
      "px_exponent": -8,
      "tick_size": 100,
      "size_decimals": 5,
      "initial_margin_bps": 500,
      "maintenance_margin_bps": 250,
      "transfer_margin_floor_bps": 1000,
      "status": "active",
      "reduce_only": false,
      "change_count": 4
    }
  ]
}

    After the snapshot, each changed market is sent alone:

    {
  "type": "SymbologyMarketUpdate",
  "market": {
    "id": 7,
    "symbol": "BTC",
    "quote": "USDC",
    "pyth_feed_id": 1,
    "max_funding_rate_e8": 10000,
    "px_exponent": -8,
    "tick_size": 100,
    "size_decimals": 5,
    "initial_margin_bps": 500,
    "maintenance_margin_bps": 250,
    "transfer_margin_floor_bps": 1000,
    "status": "inactive",
    "reduce_only": false,
    "change_count": 5
  }
}

    Clients apply an update only when its change_count is newer than the cached count for that same market id. Counts for different market ids are independent.

    Symbology fields:

    Field Meaning
    id, symbol, quote Market ID, base symbol, and quote currency
    px_exponent Signed price exponent: human price is raw_price * 10^px_exponent
    size_decimals Base quantity precision: human quantity is raw_qty / 10^size_decimals
    tick_size Price tick in raw price units; signed-order price validation also enforces the accepted price grid
    pyth_feed_id Oracle feed identifier
    max_funding_rate_e8 Maximum funding-rate magnitude, scaled by 100000000
    initial_margin_bps, maintenance_margin_bps, transfer_margin_floor_bps Margin rates in basis points (100 means 1%)
    status active, deactivating, settling, or inactive
    reduce_only Whether the market restricts trading to reducing positions
    change_count Market metadata change counter

    For the example's px_exponent = -8 and size_decimals = 5, a price of 5000000000000 means 50000 quote units per BTC, and a quantity of 100000 means 1 BTC. Its 50000 USD notional is 50000000000 monetary units. See Numeric units for collateral, fees, PnL, and funding; symbology does not supply a separate monetary exponent.

    When a subscribed market becomes inactive, the gateway first sends its SymbologyMarketUpdate, removes every subscription for that market on the connection, and then sends:

    {
  "type": "MarketUnsubscribed",
  "market_id": 7,
  "reason": "inactive"
}

    Clients choose market subscriptions after processing the initial snapshot and continue processing symbology updates on the same WebSocket connection.

    Every connection also receives an ExchangeConfigSnapshot containing the same nine fields as GET /v1/config. Later changes use the identical payload with "type":"ExchangeConfigUpdate".

    subscribe_market (public)¶

    Request:

    { "type": "subscribe_market", "symbol": 7 }

    Fields:

    • type: literal string subscribe_market
    • symbol: active symbology market id (uint32 on the wire; for example 7)

    Success:

    { "type": "ack", "status": "accepted" }

    Failure example:

    { "type": "ack", "status": "rejected", "reason": "invalid_symbol" }

    Streaming behavior:

    • subscribe_market is the native public raw market-data stream.
    • Raw BookSnapshot, BookDelta, and Trade payloads include the stream sequence in seq.
    • Raw BookSnapshot and BookDelta payloads on this stream carry bookType: "maker" or bookType: "taker".
    • Raw BookSnapshot and BookDelta payloads carry the current oracle-derived mark_price; it is 0 until the matcher has a valid oracle price.
    • Clients should filter book events by bookType if they only want one view.
    • Raw Trade events remain on this stream.
    • Raw FundingIndex events are also delivered on this stream when funding index updates are published for a subscribed market.
    • stream_reset payloads for this stream also carry bookType, and unfiltered recovery may emit one reset for maker and one for taker.

    Book synchronization and recovery¶

    Maintain separate books and cursors for each (market id, bookType) pair. A maker snapshot or delta does not establish the taker book's state.

    1. Subscribe after reading symbology. Until a BookSnapshot arrives, the book is unsynchronized; do not use standalone deltas as a complete book.
    2. A snapshot replaces all cached bids and asks for its pair. Store its book_cursor. depth_cap and truncated, when supplied, describe the published view; absence of a level outside that view does not prove there are no orders at that price.
    3. For a delta, require nonzero cursors and prev_book_cursor == stored_book_cursor. Apply it, then store its book_cursor. Cursors need not increase by exactly one. Use the cursor link, not arithmetic on seq, to test book continuity.
    4. Each delta level is the new absolute quantity at its price on that side. Replace that side's quantity; qty = 0 removes that side's level. Prices absent from the delta stay unchanged. For example, a bid of 500000 followed by a delta of 700000 becomes 700000, not 1200000. order_count, when supplied, is also an absolute value.
    5. If the cursor link fails or stream_reset arrives, discard the affected book and cursor, mark it unsynchronized, and send subscribe_market again for that market. Wait for a fresh snapshot. A reset identifies the market in symbol and the affected view in bookType; an unfiltered subscription can receive resets for both views.

    The reference clients buffer a bounded number of deltas while awaiting a snapshot and apply only a chain linked from its cursor. An independent client may instead discard those deltas and request another snapshot if it cannot prove continuity. Do not merge unlinked deltas into a fresh snapshot.

    On WebSocket disconnect, invalidate the subscribed books. Reconnect, process the new symbology snapshot, and resubscribe to active markets. Trade and FundingIndex are separate events; they do not replace book levels or advance your stored book cursor. seq can skip because other events share the stream. If MarketUnsubscribed reports an inactive market, clear its local book and subscriptions rather than repeatedly resubscribing to that inactive market.

    • signature_b64: base64-encoded ed25519 signature over the exact auth_challenge.message bytes
    • signed_payload_b64: optional base64-encoded Solana off-chain V0 signed payload. When present, the Ledger prefix and body are verified and the signature is checked over the full signed payload.

    Rules:

    • Challenge TTL is 60s.
    • Challenge is single-use (replay rejected).

    • Delegate-authenticated sessions may submit orders, cancels, modifies, vault operations, and subaccount transfers.
    • Collateral withdraw requires owner wallet authentication; delegate-authenticated sessions are rejected for signed_withdraw.

    Delegate rotation warning:

    • Before changing a wallet's delegate key, cancel all open orders for that wallet.
    • Existing resting orders are not automatically canceled when the delegate changes.
    • Orders signed by a previous delegate may fail settlement after the delegate key is updated.

    { "type": "ack", "status": "accepted" }

    Ledger Hardware Wallet Signing¶

    Ledger Solana hardware wallets sign Solana off-chain message payloads, not the raw gateway message bytes. Ledger clients should use Solana off-chain message V0 signing.

    V0 signed payload layout:

    0xff || "solana offchain" ||
version(1) ||
app_domain(32) ||
format(1) ||
signer_count(1) ||
signer_pubkey(32) ||
message_len_le_u16(2) ||
message_body

    Gateway Ledger clients use:

    version = 0
app_domain = "aethon-gateway" padded with zero bytes to 32 bytes
format = 0
signer_count = 1
signer_pubkey = wallet pubkey bytes

    The V0 prefix before message_body is 85 bytes.

    Auth challenge Ledger body:

    AETHON_AUTH_V1|<wallet_pubkey>|<nonce>|<iat>|<exp>|<session_id>

    This is the exact auth_challenge.message encoded as UTF-8.

    signed_set_delegate Ledger body:

    base64(owner_pubkey || delegate_key || delegate_nonce_le_u64 || request_id64_le_u64 || iat_le_u64 || exp_le_u64)

    The base64 wrapper is used because the set-delegate payload contains binary bytes, while Ledger Solana off-chain V0 message bodies must be valid text.

    Account synchronization and recovery¶

    Authentication and subscribe_account acknowledgements do not establish account readiness. Wait for a valid AccountSnapshot before making decisions from balances, positions, working orders, or conditional groups.

    • Treat the snapshot as replacement state for the authenticated wallet, including its arrays of subaccounts, positions, working orders, and TP/SL groups. Remove cached entries absent from the new snapshot. Set the account state watermark to last_seq; do not apply already-covered fills again.
    • Apply subsequent account-state lifecycle events only when their seq is greater than that watermark, then advance it. Sequences are not contiguous for one wallet: a jump by more than one is not by itself an account gap. Public book seq and private account sequences are not interchangeable.
    • UserDepositAddressStatus is an exception: it acknowledges a registration command, which the account snapshot does not represent. It can arrive with seq <= last_seq. Still correlate and process that acknowledgement by subaccount and request timestamps, without moving the state watermark backward or changing balances from it.
    • The gateway can send a fresh account snapshot when its upstream recovers, even while your WebSocket remains connected. Install a newer snapshot as replacement state. Ignore older snapshots within the same session. On a new session, bootstrap from the fresh snapshot rather than treating the old cached state as current.
    • On disconnect, suspend new submissions, reconnect, authenticate, and send subscribe_account again. Reconcile the fresh snapshot and synchronized market data before resuming. AccountSnapshotError means bootstrap has failed; an earlier accepted acknowledgement does not make that account ready. session_preempted means another authenticated session owns the wallet; stop instead of competing in a reconnect loop.

    The public subscription has no start_seq replay parameter. A fresh snapshot recovers current state, not every event missed during the disconnect. Use get_order_history and get_order_events to reconcile terminal orders and missed fills/settlements, and get_funding_history for funding records. History pagination has its own cursors; it does not advance the live account watermark.

    Persist submitted instruction IDs and observed order IDs so an ambiguous disconnect can be reconciled. Check working orders, conditional groups, and history before retrying an order, cancel, or TP/SL command. An order absent from working_orders may already have filled, expired, or been cancelled. A client instruction ID correlates a command; do not assume that resending it provides an exactly-once submission guarantee.

    Track each fill leg by wallet, subaccount, external order ID, and trade_id when available. Fill, FillSettled, and FillBusted are different stages of that same fill, not duplicate messages. Do not discard a settlement because its trade ID was already seen in a provisional fill, or merge two order legs of the same trade. Use the live sequence watermark to avoid applying the same state event twice; use order history when a legacy event lacks a trade ID.

    For a reduce-only result, FillSettled remains one event at one seq and keeps qty and fee as the provisional matched quantity and requested fee. It additionally includes trade_id, settled_qty, reduced_qty, applied_fee, adjustment_reason: "reduce_only", and three per-order-leg booleans: reduce_only_leg, limiting_leg, and exhausted_leg. These booleans identify whether this account's leg was reduce-only, constrained the settled quantity, and consumed all of its on-chain reduce-only capacity, respectively. The quantity invariant is qty = settled_qty + reduced_qty; zero and false values are emitted explicitly.

    Use settled_qty and applied_fee to reconcile actual position changes and fees; qty and fee remain provisional. See TP/SL and reduce-only for settlement and manual-close examples.

    String enum values in private account events use:

    • side: BID or ASK
    • role: MAKER or TAKER
    • tif: GTC or IOC

    The shared envelope also includes the following numeric fields:

    Field Type Meaning for these events
    order_type uint8 Order kind on acceptance; otherwise an unused zero unless specified
    price uint64 Order/fill price where defined; unused zero on cancel outcomes
    delta_ppm int32 Order offset/protection on acceptance; otherwise unused zero
    execution_mode uint8 Order mode on acceptance/fill; otherwise unused zero
    status, error_code uint8, uint32 Terminal settlement result where defined; otherwise unused zeros

    The shared serializer emits order_type, price, delta_ppm, execution_mode, status, error_code, vault_id, position_index, and phase even when their value is zero. Interpret them only where the event definition gives them meaning. For example, status: 0 on OrderAccepted does not mean the order has settled, and order_type: 0 on a Fill does not establish the original order type.

    Other optional numeric/string fields are normally omitted when zero/empty. For example, an absent fee means zero, and an absent cancel reason means zero. Two exceptions are always explicit: matcher Fill.remaining_qty, including zero, and all reduce-only settlement adjustment fields, including zero quantities/fees and false booleans. Ignore unknown response fields for forward compatibility; request envelopes retain their documented strict JSON validation.

    get_order_history (private, paginated)¶

    Request:

    {
  "type": "get_order_history",
  "request_id": "hist-1",
  "created_from_unix_s": 1735689600,
  "created_to_unix_s": 1738368000,
  "cursor": "",
  "limit": 20
}

    Fields:

    • type: literal string get_order_history
    • request_id: optional caller-supplied correlation id; echoed back in the response so multiple in-flight pages can be matched up
    • created_from_unix_s: optional inclusive lower bound on order creation time, as UTC Unix seconds
    • created_to_unix_s: optional exclusive upper bound on order creation time, as UTC Unix seconds
    • cursor: optional opaque string from the previous page's next_cursor; empty or omitted returns the newest page
    • limit: optional page size; clamped to 1..100, defaults to 20

    Rules:

    • Requires an authenticated wallet-bound session (same gating as subscribe_account).
    • Orders are returned for the authenticated bound wallet only; the request does not accept a wallet override.
    • Creation-time filtering uses the half-open interval [created_from_unix_s, created_to_unix_s). Either bound may be omitted for an open-ended query. Supplied bounds must be non-negative integers, and created_from_unix_s must be less than created_to_unix_s when both are present. JSON null is invalid; omit an unused bound instead.
    • next_cursor binds the first page's creation-time bounds. Later pages may omit the bounds and use the cursor alone. If either bound is supplied with a cursor, it must match the bound encoded in that cursor.
    • Strict JSON: unknown fields are rejected with invalid_get_order_history.

    Notes:

    • Orders are ordered most-recent-first by last_event_seq (i.e. by the seq of the last persisted history event for the order).
    • next_cursor is omitted when there are no more rows; pass it back verbatim in the next request to page older.
    • A cursor preserves the first page's event-sequence snapshot and creation-time bounds. Events persisted after that snapshot are excluded from later pages and appear when pagination is restarted without a cursor.
    • Pagination is by distinct order. The page selects orders by last_event_seq and returns one flat row per order.
    • status is one of open, filled, canceled, rejected.
    • execution_mode preserves the accepted order's mode (4 for reduce-only) when present in persisted history; older rows may omit it.
    • side is BID for buys and ASK for sells, matching working_orders and Fill events.
    • price, original_qty, remaining_qty, filled_qty, settled_qty, busted_qty, and reduced_qty are raw integers interpreted using the market's symbology metadata, identical to other private/account events.
    • filled_qty, settled_qty, busted_qty, and reduced_qty are aggregated from persisted fill/settlement events for the order. reduced_qty is quantity removed by reduce-only settlement and is distinct from a failed-settlement bust.
    • Conditional child rows include conditional_group_external_order_id and conditional_leg (1 = TP, 2 = SL) when their association is available. These fields link each active child ID to its group across trigger cycles.
    • event_reason_code and reject_reason_code on the top-level order mirror the latest terminal reason when available.
    • Detailed lifecycle events are fetched separately with get_order_events.

    Common rejects:

    • auth_required (no active authenticated WS session)
    • invalid_get_order_history (malformed request payload)
    • invalid_order_history_cursor (cursor is malformed, unsupported, or conflicts with an explicitly supplied creation-time bound)
    • invalid_order_history_created_from (created_from_unix_s is null or not a non-negative integer)
    • invalid_order_history_created_to (created_to_unix_s is null or not a non-negative integer)
    • invalid_order_history_created_range (equal or inverted creation-time bounds)
    • stream_unavailable (the account-history service is unavailable)
    • order_history_unavailable (the order-history request failed)

    Rejected ack responses echo request_id when supplied.

    Request:

    {
  "type": "user_deposit_address",
  "subaccount_id": 0,
  "client_unix_ns": 1710000000000000000

    Fields:

    • subaccount_id: target trading subaccount id (uint64)

    Rules:

    • Requires an authenticated wallet-bound session.
    • The wallet is the authenticated bound wallet. The request does not accept a wallet override.
    • The request does not include amount, token account, deposit address, transaction bytes, or VAA bytes.
    • This request registers the derived EVM deposit address for the authenticated wallet and subaccount. It does not transfer collateral or specify an amount.
    • The actual deposit amount is determined from the later EVM token transfer.

    • wallet: the authenticated bound wallet as 32 bytes.
    • subaccount_id: uint64, encoded big-endian for the CREATE2 salt input.

    Formula:

    salt = keccak256(wallet || uint64_be(subaccount_id))
user_deposit_address = last20bytes(
  keccak256(0xff || evm_vault || salt || userDepositInitCodeHash)
)

    Clients should fetch GET /v1/evm/addresses from the same gateway they use for WebSocket commands instead of hardcoding local deployment artifacts.

    • A successful submission does not emit a generic ack accepted.
    • Wait for the matching UserDepositAddressStatus event. It confirms that the wallet/subaccount deposit address is registered.

    Software-signed proof construction¶

    Unless a command section states otherwise, a software-signed proof uses this Ed25519 message:

    ascii(signature_domain) || 0x00 || unsigned_proof_bytes

    unsigned_proof_bytes is the raw proof prefix and decoded command payload in the exact field order documented for that command. It excludes both signer_pubkey and signature. The transmitted raw proof is:

    unsigned_proof_bytes || signer_pubkey[32] || signature[64]

    All integer fields in these proofs are little-endian unless a command section explicitly says otherwise. Sign the domain bytes and the single NUL delimiter; the delimiter is part of the message. iat and exp in signed proofs are UTC Unix seconds.

    signed_order¶

    Request:

    { "type": "signed_order", "msg_b64": "<base64 signed order proof bytes>" }

    Envelope fields:

    • type: literal string signed_order
    • msg_b64: base64 of the raw signed order proof bytes

    Raw proof definition:

    • Wire length: 191 bytes
    • Signature domain: AETHEON_ORDER_V1
    • The raw proof is not JSON. It contains:
    • sender_pubkey [32]byte
    • partition_id u16
    • subaccount_id uint64
    • iat uint64
    • exp uint64
    • order ContractOrderV1
    • signer_pubkey [32]byte
    • signature [64]byte

    Decoded ContractOrderV1 fields:

    • symbol uint32
    • price uint64
    • qty uint64
    • tif uint8
    • order_type uint8
    • execution_mode uint8
    • role uint8
    • delta_ppm int32
    • side uint8
    • request_id64 uint64

    Allowed enum values:

    • tif: 0 = IOC, 1 = GTC
    • order_type: 0 = LIMIT, 1 = MARK_TO_MID, 2 = MARKET
    • execution_mode: 0 = NORMAL, 1 = MAINTENANCE_LIQUIDATION, 2 = ADL, 3 = VAULT_LIQUIDATION, 4 = REDUCE_ONLY
    • role: 0 = MAKER, 1 = TAKER
    • side: 0 = BUY, 1 = SELL

    These enum values are the public signed-wire values.

    Role-based command timing:

    The sequencer's taker delay defaults to 300 ms; deployments can configure another delay. The rules below use that default.

    • Taker orders become eligible to enter an auction after 300 ms.
    • Maker orders are eligible for the next auction.
    • The same role-based timing applies to cancels and modifies. Maker cancels and maker modifies are eligible for the next auction; taker cancels and taker modifies become eligible after 300 ms.
    • The cancel/modify role must match the live order role, so a taker cannot bypass this timing by marking a command as maker.

    Price and quantity encoding¶

    • price is a raw uint64 integer carried in wire format; the market's px_exponent is applied to interpret it as a decimal price.
    • Human price is price * 10^(px_exponent).
    • Example: if px_exponent = -2 and price = 10001, the human price is 100.01.
    • qty is a raw uint64 integer carried in wire format in units of 10^(-size_decimals) for that market.
    • Human quantity is qty * 10^(-size_decimals).
    • Risk View requires raw order quantity to fit a signed 64-bit integer: 1..9223372036854775807, despite the unsigned wire field.
    • To encode a human decimal quantity, clients compute raw_qty = human_qty * 10^(size_decimals).
    • A human decimal quantity is valid only if it is exactly representable at that market resolution and raw_qty > 0.
    • This means a client decimal input may have at most size_decimals fractional digits.
    • Examples:
    • BTC with size_decimals = 5: minimum increment is 0.00001; 10.12345 is valid and encodes as 1012345; 10.123456 is invalid because it is not exactly representable as uint64 qty
    • ETH with size_decimals = 4: minimum increment is 0.0001; 10.1234 is valid and encodes as 101234; 10.12345 is invalid because it is not exactly representable as uint64 qty

    Limit-price acceptance rule:

    • The gateway validates the price field only for LIMIT orders.
    • The rule is based on 6 - size_decimals.
    • Starting from the scaled decimal price, trailing zeros are stripped first.
    • After stripping trailing zeros:
    • remaining decimal places must be <= 6 - size_decimals
    • if any decimal places remain, the normalized price must have at most 5 significant figures
    • Clients must apply this rule before submitting an order.

    Equivalent intuition:

    • More size_decimals leaves fewer decimal places available for price.
    • When decimal places remain, prices are limited to 5 significant figures after normalization.

    Rules enforced by gateway:

    • request_id64 is passed through unchanged. It is client-defined metadata and may be a nonce, sequence number, trace ID, 0, or otherwise unused.
    • Bit 63 of request_id64 is reserved for system use. Public gateway clients must leave it clear.
    • symbol must be active symbology and fit in uint32
    • qty must be > 0
    • For signed raw integer orders, representable quantity precision is implied by the wire encoding above; clients accepting human decimal qty input must reject values with more than size_decimals fractional digits
    • Public gateway clients may submit only execution_mode = 0 = NORMAL or execution_mode = 4 = REDUCE_ONLY. Modes 1, 2, and 3 are reserved for internal liquidation workflows.
    • role must be explicitly provided as MAKER or TAKER; gateway does not infer it from order_type or tif
    • LIMIT orders require price > 0
    • LIMIT orders require the raw price to satisfy the gateway's accepted price grid for that symbol (px_exponent, size_decimals, 6 - size_decimals, 5-significant-figure rule)
    • MARK_TO_MID orders allow negative, positive, or zero delta_ppm
    • MARK_TO_MID orders do not use the price field for gateway validation
    • MARK_TO_MID orders require a current mark price in gateway for precheck; the final executable limit is determined at auction time from Pyth
    • MARK_TO_MID orders accept the full signed 32-bit delta_ppm range; the matcher rejects only when the derived auction-time price is invalid or cannot be represented on the symbol price grid
    • MARKET orders require tif = IOC and role = TAKER
    • MARKET orders may use price as a reference price and positive delta_ppm as the maximum adverse slippage
    • MARKET orders with price = 0 require delta_ppm = 0; this 0/0 combination is an unrestricted market order
    • MARKET orders with price > 0 are protected market orders and require delta_ppm > 0
    • protected MARKET orders require delta_ppm <= 1000000, i.e. at most 100% adverse slippage
    • MARKET orders require delta_ppm >= 0; zero is valid only for the unrestricted price = 0, delta_ppm = 0 combination
    • exp must be > 0. The gateway admission deadline is the earlier of signed exp and iat + 5 seconds. The signed proof bytes are not mutated.
    • iat is the client send time in Unix seconds; the gateway converts it to nanoseconds for event timing fields.

    Order lifetime after admission:

    • The gateway's five-second admission window does not shorten an admitted GTC order's signed exp. A GTC order can remain live until that expiry, unless filled or cancelled earlier.
    • Ordinary IOC orders have a matching deadline of the earlier of signed exp and iat + 5 seconds. Unfilled quantity is cancelled after their eligible auction; the deadline does not give them repeated auctions.
    • A successful modify replaces the working GTC order's expiry with the modify proof's signed exp, even if price and quantity stay unchanged.

    For example, a GTC order signed at 12:00 with exp at 13:00 must reach the gateway before 12:00:05, but it can remain live until 13:00.

    Mark-to-mid price semantics:

    • For MARK_TO_MID, clients should treat price as ignored and usually send 0.
    • The gateway does not apply the LIMIT price-grid rule to MARK_TO_MID.
    • The executable limit is determined at auction time from the current Pyth mark and delta_ppm.
    • delta_ppm is parts per million of that auction-time mark price.
    • A zero delta_ppm derives the current mark price before matcher price-grid snapping.
    • The raw price delta is floor(mark_price * abs(delta_ppm) / 1_000_000), with a minimum of one raw price unit for nonzero delta_ppm.
    • Effective limit derivation:
    • buy: derived_limit = mark_price - raw_delta when delta_ppm > 0, and mark_price + raw_delta when delta_ppm < 0
    • sell: derived_limit = mark_price + raw_delta when delta_ppm > 0, and mark_price - raw_delta when delta_ppm < 0
    • Positive delta_ppm moves buys below mark and sells above mark.
    • Negative delta_ppm moves the raw derived buy above mark and the raw derived sell below mark.
    • The derived limit is snapped to the market price grid without worsening the owner price: buys snap down and sells snap up. A small negative delta may therefore snap back to the current grid level instead of crossing.
    • The symbol's explicit limit-price grid affects LIMIT orders directly, while MARK_TO_MID is governed by mark availability, delta_ppm, the validity of the derived price, and price-grid snapping.

    Market-order slippage semantics:

    • For a protected MARKET order, price is the client-supplied reference price and delta_ppm is parts per million of that reference price.
    • The raw adverse-price allowance is floor(price * delta_ppm / 1_000_000).
    • A protected buy may execute at or below price + allowance.
    • A protected sell may execute at or above max(price - allowance, 0).
    • Prices farther in the favorable direction remain eligible; the protection is one-sided.
    • Eligibility is evaluated against the auction fill price. The reference price is not added as a clearing-price candidate.
    • The reference price and slippage are used unchanged, without applying the LIMIT price-grid rule to them.

    "symbol": 7,

    Reduce-only order semantics:

    • Set execution_mode = 4 in the signed order proof; the JSON envelope remains signed_order with msg_b64, without a top-level reduce_only field.
    • Sells reduce a long position; buys reduce a short position in the same subaccount and symbol. At settlement, quantity is clipped to available reducing capacity, including zero while flat or on the wrong side. An exit cannot increase exposure or reverse the position.
    • A matched Fill is provisional. Reconcile a reduce-only FillSettled using settled_qty and applied_fee, including zero; reduced_qty is the quantity removed from the match. It is distinct from a failed-settlement bust.
    • A successful reduce-only close that exhausts a position invalidates TP/SL groups protecting that position direction. An unrelated normal close does not automatically cancel them. See TP/SL and reduce-only for quantity and manual-close examples.

    signed_conditional_group¶

    Request:

    { "type": "signed_conditional_group", "version": 1, "msg_b64": "<base64 signed conditional-group proof bytes>" }

    The proof is 196 bytes and uses signature domain AETHEON_COND_V1. Its envelope contains, in order, the sender [32]byte, partition uint16, subaccount uint64, iat uint64, exp uint64, the 42-byte conditional group, signer [32]byte, and signature [64]byte. Integers are little-endian with no padding; iat and exp are Unix seconds. The JSON envelope version is required and must be 1.

    Conditional group fields, in wire order:

    • symbol uint32
    • qty uint64
    • exit_side uint8: 0 = BUY, 1 = SELL
    • leg_flags uint8: bit 1 = take profit, bit 2 = stop loss
    • tp_trigger_sources and sl_trigger_sources uint8: bit 1 = oracle, bit 2 = auction; sources may be combined
    • version uint8: must be 1
    • activation_mode uint8: 0 = parent_fill, 1 = immediate
    • tp_trigger_price and sl_trigger_price uint64; a take-profit child uses its trigger price as its limit price
    • request_id64 uint64

    Rules enforced by the gateway and Risk View:

    • At least one conditional leg is enabled and qty is between 1 and 9223372036854775807 inclusive.
    • Enabled trigger prices must lie on the market price grid; disabled leg fields must be zero.
    • When both legs are enabled, stop loss must be below take profit for a sell exit. The comparison is reversed for a buy exit.
    • The take-profit child limit is derived from its trigger price.
    • In parent_fill mode, bind a subsequently submitted normal parent with the same wallet, symbol, and subaccount, quantity at least the group's signed qty, and the opposite side. Protection grows from successfully settled parent fills up to the group's signed qty, not the full net position or unrelated fills. Residual exposure can rearm after child settlement; later settled parent fills can add protection.
    • In immediate mode, no parent is submitted. The subaccount must have a position reduced by exit_side. The group starts with submitted qty, which is not automatically resized by unrelated trades.
    • Both activation modes can rearm residual protected quantity after the selected child and its pending settlements are resolved.
    • A successful parent modification invalidates its TP/SL group. A child already active or being activated remains a live ordinary order, is not rearmed by Bop, and is the trader's responsibility to monitor or cancel.
    • exp is required and may be at most 90 days after gateway admission.

    Take-profit legs become TAKER, REDUCE_ONLY GTC limit orders at the TP trigger price. Stop-loss legs become TAKER, REDUCE_ONLY unrestricted market IOC orders with price = 0 and delta_ppm = 0; the SL trigger is not an execution-price guarantee. The group and each enabled leg receive distinct external order IDs. Conditional groups are immutable; cancel and replace a group to change it.

    See TP/SL and reduce-only for trigger directions, activation flows, exit sizing, and cancellation behavior after manual trades.

    signed_conditional_parent¶

    Request:

    {
  "type": "signed_conditional_parent",
  "version": 1,
  "conditional_group_external_order_id": "101",
  "msg_b64": "<base64 signed order proof bytes>"
}

    This command binds a normal signed order to a previously approved parent_fill group; it cannot bind an immediate group. msg_b64 uses the same order proof and AETHEON_ORDER_V1 signature domain as signed_order. The JSON envelope version is required and must be 1; conditional_group_external_order_id is the ID received in ConditionalApproved. Send this backend-assigned ID back as a decimal string to identify the group to bind to the parent. JSON numbers are rejected for this request field.

    Submit the parent only after receiving ConditionalApproved. Bop verifies that the parent has the same wallet, subaccount, and symbol as the group, has quantity at least the group's signed qty, and has the opposite side from the conditional exit. Risk then evaluates the parent as a normal new order. OrderAccepted or OrderReject is the authoritative parent result. For a group in waiting_parent, a binding mismatch, such as a smaller quantity, rejects the attempted parent with ConditionalInvalidGroup while leaving the group in waiting_parent; submit an eligible parent or cancel the unused group. If a successfully bound parent is rejected with no settled or pending fills, Bop completes the unprotected group with ConditionalCompleted; wait for that event to confirm completion. A timeout or disconnect is ambiguous, so the client must wait for the account stream or reconnect and use its snapshot rather than guessing whether the parent was accepted.

    signed_conditional_cancel¶

    Request:

    { "type": "signed_conditional_cancel", "version": 1, "msg_b64": "<base64 signed cancel proof bytes>" }

    This command uses the existing AETHEON_CANCEL_V2 proof format. Set external_order_id to the conditional group ID, not a take-profit or stop-loss leg ID. The JSON envelope version is required and must be 1.

    Group cancellation applies while waiting for a parent or settled fill, or while dormant. It can be rejected once activation starts. Cancel an accepted active child with signed_cancel using ConditionalTriggered.selected_external_order_id; successful user child cancellation terminates the bracket without rearming residual exposure.

    ping¶

    Request:

    { "type": "ping", "client_unix_ns": 1735689600000000000 }

    Fields:

    • type: literal string ping
    • client_unix_ns: required integer timestamp supplied by the client.
    • No other request fields are accepted.

    Success:

    { "type": "pong", "client_unix_ns": 1735689600000000000 }

    RTT usage:

    • The gateway echoes client_unix_ns unchanged.
    • The client should capture a local timestamp immediately before send and another local timestamp when the pong is received.
    • A simple RTT estimate is client_recv_unix_ns - pong.client_unix_ns.
    • This measures application-layer round-trip time from the client clock domain. It does not measure one-way client->gateway latency.
    • The gateway does not provide a server timestamp for RTT calculation because that would mix clock domains and be sensitive to clock drift.

    Minimal End-to-End Flows¶

    Flow A: wallet direct signing (no delegate)¶

    1. auth_wallet with wallet_pubkey + expiry_seconds.
    2. Receive auth_challenge.
    3. Sign challenge, send auth_response, and wait for ack accepted.
    4. Send subscribe_account and wait for AccountSnapshot before submitting trading commands.
    5. Before transferring EVM deposit tokens, send user_deposit_address and wait for the matching UserDepositAddressStatus so the wallet/subaccount EVM deposit address is registered.
    6. Transfer collateral to that address, then wait for UserCollateralUpdate before treating the trading subaccount as funded.
    7. Send signed_order / signed_cancel / signed_modify / signed_conditional_group / signed_conditional_parent / signed_conditional_cancel / signed_withdraw / signed_create_vault / signed_deposit_vault / signed_withdraw_vault / signed_transfer_subaccount.
